# Verification Strategy Review — Codex

## Summary
The prompt is directionally right, but it assumes shared identifiers, shared defaults, and trustworthy cached/stable Excel values. Those assumptions are false in the local workbook, so the overnight run can both false-fail and false-pass unless it normalizes country names, sets every dashboard input explicitly, and classifies workbook/data issues separately from true parity diffs.

## Findings

| # | Category | Severity | Finding | Recommendation |
|---|----------|----------|---------|----------------|
| 1 | VALID BUG | HIGH | The workbook country selector is not ISO3. Local workbook inspection shows `Dashboard!C12` is a dropdown sourced from `Macrofiscal!$A$67:$A$264`, which contains country names, while the prompt writes `UGA`/`USA`/`MDV` (`prompts/VERIFICATION-PROMPT.md:99-121`, `:138-156`). The extraction pipeline also exists largely to map workbook names to ISO3 (`scripts/extract_excel_data.py:21-138`). Writing ISO3 to Excel will produce `MATCH()` misses and stable-on-error false fails. | Drive Excel with workbook country names, not ISO3. Build an explicit `iso3c <-> workbook country name` map from the parquet `country` column or the extractor's name map, and log both identifiers in the report. |
| 2 | VALID BUG | HIGH | The Phase 0 example mapping is materially wrong. The prompt guesses `Dashboard!B3` / `Dashboard!B5:B7` and a `Results` sheet (`prompts/VERIFICATION-PROMPT.md:53-63`), but the workbook actually uses `Dashboard!C12`, `C17`, `C20:C21`, `C24:C25`, `C28:C29`, `C33:C34`, and `C38`, with output sheets `Output Baseline` / `Output Scenarios` plus raw calc sheets `Baseline`, `Paris`, etc. There is no `Results` sheet. | Replace the guessed example with the real cells/sheets. For parity, compare raw yearly cells from `Baseline` and the scenario sheets, not a guessed `Results` table or top-level chart summaries. |
| 3 | VALID BUG | HIGH | The prompt treats "default" as shared across Excel and Python, but the defaults already diverge. The workbook dashboard currently caches `inflation_start=3.5`, `inflation_end=3.5`, `debt_target=60`, while engine defaults are `inflation_start=5.0`, `inflation_end=3.5`, `debt_target=50.0` (`packages/qcraft-engine/src/qcraft_engine/constants.py:38-48`). Phase 1 even compares `run_pipeline(data, "UGA")` to Excel without setting all inputs (`prompts/VERIFICATION-PROMPT.md:150-158`). | Before every comparison, set every dashboard input explicitly in Excel and pass the same params into `run_pipeline()`. Do not rely on workbook state or engine defaults for any phase. |
| 4 | VALID BUG | HIGH | The openpyxl cached-country fallback is not trustworthy evidence. In the local workbook, `data_only=True` shows `Dashboard!C12 = Afghanistan`, but many `Output Baseline` and `Output Scenarios` summary cells are already `#VALUE!`. That makes the Phase 0 "cached-country anchor" and the Phase 1 fallback (`prompts/VERIFICATION-PROMPT.md:48-49`, `:160-166`) unsafe. | Treat cached outputs as diagnostics only. If xlwings cannot recalc, classify the run as `WORKBOOK_RECALC_FAILURE` or `CACHE_INVALID`; do not convert cached values into pass/fail parity claims. |
| 5 | VALID BUG | HIGH | The recalc handshake can false-complete on stale or error values. The prompt declares success if one output cell repeats 3 times (`prompts/VERIFICATION-PROMPT.md:96-123`). An unchanged `#VALUE!`, `#N/A`, or stale cached number is "stable" by that definition. This is especially risky because the workbook has external links and existing cached errors. | Gate on a small sentinel set, not one cell: requested dashboard value echoed correctly, an upstream sheet updated, and final comparison cells are numeric/non-error. Stability should mean "consistent and valid," not just "unchanged." |
| 6 | VALID BUG | MED | `±0.5pp` is far looser than the repo's stated parity bar. The spec says `±0.1 pp for ratios` (`planning/SPEC.md:40`, `:55`) and current fiscal/climate parity-style tests use `abs=0.01` (`packages/qcraft-engine/tests/test_fiscal.py:305-320`, `packages/qcraft-engine/tests/test_climate.py:392-399`). Also, `test_golden_masters.py` is mostly fixture existence + two spot checks, so it is not a reliable tolerance oracle by itself (`packages/qcraft-engine/tests/test_golden_masters.py:44-128`). | Do not label `<=0.5pp` as clean parity. Use two bands: `PASS <= 0.1pp`, `REVIEW 0.1-0.5pp`, `FAIL > 0.5pp`, and always report exact diffs. |
| 7 | VALID BUG | MED | The Phase 2 sample is not actually runnable as written. `SSD` and `GRD` are missing from the engine's all-datasets intersection because both are absent from productivity data; `get_country_list()` explicitly filters to countries present in all four sources (`packages/qcraft-engine/src/qcraft_engine/data_loader.py:55-78`). Those countries would surface as Python/data errors, not parity bugs. | Build the country sample from `get_country_list()` or run a preflight availability check and classify `ENGINE_DATA_GAP` separately from `PARITY_FAIL`. |
| 8 | VALID BUG | HIGH | The Phase 3 `expenditure_rigidity` combos do not test what the prompt claims unless climate scenario outputs are compared. In the engine, `expenditure_rigidity` is only used inside `calc_climate_scenario()` (`packages/qcraft-engine/src/qcraft_engine/climate.py:21-27`, `:226-231`), and workbook inspection shows `Dashboard!C38` feeds the scenario sheets, not the baseline sheet. If Phase 3 only compares baseline outputs, `flexible` vs `sticky` is a no-op. | For rigidity tests, compare at least one climate scenario sheet, not just baseline. `Hot Unadapted` debt-to-GDP and primary expenditure are enough to exercise the branch without expanding scope too much. |
| 9 | VALID ADDITION | MED | `no_rule` itself is correctly named, but the overall Phase 3 branch coverage is still thin. The workbook fiscal rule dropdown is `Dashboard!C33`, sourced from `Baseline!C50:C51 = Yes/No`, and the engine expects the exact strings `"Yes"` / `"No"` (`packages/qcraft-engine/src/qcraft_engine/fiscal.py:39-40`, `:167-175`, `:239-247`). The larger gap is that the prompt never leaves `"Nominal interest rate"`, even though both workbook and engine have three interest-rate modes. | Keep `no_rule`, but replace one other combo with `Interest-growth differential` or `Real interest rate` so Phase 3 hits a real additional branch instead of only changing debt target levels. |
| 10 | VALID ADDITION | MED | Sampling only `2030, 2040, 2050, 2070, 2099` can miss a divergence that peaks in between, and once the yearly row/table is loaded, comparing the full path is cheap. The prompt is paying the Excel recalc cost already; five checkpoints save little but materially increase false-pass risk (`prompts/VERIFICATION-PROMPT.md:143-158`, `:270-276`). | Compare the full `2030-2099` series for the chosen metrics and report the worst absolute diff and its year. If a summary is needed, keep the checkpoints in the report but compute status from the full path. |
| 11 | VALID ADDITION | HIGH | The report taxonomy is too coarse to separate real engine bugs from data/config mismatches. Right now the prompt mainly offers `PASS/FAIL/TIMEOUT/NOT_IN_EXCEL` (`prompts/VERIFICATION-PROMPT.md:296-314`), but the actual failure modes include name-map mismatch, engine data gap, stale/error cache, workbook recalc failure, and default/version mismatch. Without that split, an overnight report will overstate engine defects. | Use explicit statuses such as `PARITY_PASS`, `PARITY_REVIEW`, `PARITY_FAIL`, `EXCEL_SELECTION_ERROR`, `EXCEL_RECALC_ERROR`, `ENGINE_DATA_GAP`, `CACHE_INVALID`, and `CONFIG_MISMATCH`. That is the minimum needed to tell "real bug" from "data mismatch." |

## Top 3 Assumptions That Need Validation
1. The Excel selector accepts the same country identifier as the engine. It does not; Excel wants workbook country names, not ISO3.
2. A repeated output value means recalculation completed successfully. It may only mean the workbook is stably wrong.
3. Workbook defaults and cached outputs are safe parity baselines. They are not; the local workbook already caches non-default values and `#VALUE!` outputs.

## Alternative Failure Modes Not Covered
- `update_links=False` can suppress prompts while leaving stale external-link values in place, which looks like a clean run but is a data-version problem.
- `openpyxl` warns that the workbook uses extended data validation; an agent that only reads `ws.data_validations` can miss the real dropdown sources for `C12`, `C17`, `C28`, and `C33`.
- Country-name normalization can fail even when the country exists in both systems. `scripts/extract_excel_data.py` already has manual mappings for names like `Côte d'Ivoire`, `Türkiye`, and `South Sudan, Republic of`.
- The spec and code disagree on some base assumptions, including the parity tolerance and projection boundary (`planning/SPEC.md:40`, `:252-257` vs `packages/qcraft-engine/src/qcraft_engine/constants.py:3-5`). The report should stamp the effective workbook/code boundary used in the run.
- Output-only checks can still false-pass through compensating errors. A minimal upstream sentinel set is needed if the run is going to claim "parity" rather than "rough agreement."
