# Change request: PIPELINE — engine assumptions that block a full-horizon refresh

**Date:** 2026-08-26 · **Lane:** 3 (TEA-1401) · **Status:** worked around, not blocked.

Three things surfaced while refreshing the Explorer's inputs to WEO April 2026.
None was fixed here — all three are engine-side, and this lane is data-side — but
each is a live constraint on the refresh.

---

## 1. The WEO horizon is pinned to 2029 in three different places

**Expected (per spec):** WEO data ends where the WEO publication ends, and the
engine finds the boundary from the data. `baseline_v1`, `fiscal` and
`interest_rate` do exactly that — `weo_max_year = int(macro_country["years"].max())`.

**Found:** two other places do not.

- `productivity_country()` takes `weo_max_year: int = 2029` and
  `data_loader.run_pipeline()` never passes it, so productivity always converges
  from 2029 no matter what the data says
  (`packages/qcraft-engine/src/qcraft_engine/productivity.py:42`).
- `data_loader._build_climate_variation()` caps the climate shock start at
  `min(country_weo_max, PROJ_START - 1)` = 2029, and `climate.py` then infers its
  own `weo_max_year` from where the variation first goes nonzero
  (`data_loader.py`, `climate.py:63-76`).

So handing the engine WEO data through 2031 — which April 2026 publishes — would
give `baseline_v1` a 2031 boundary while productivity still converged from 2029
and climate shocks still started in 2030. The 2030 and 2031 rows would be WEO
actuals in the fiscal block and post-WEO projections in the climate block at the
same time. It fails silently: no exception, just a two-year desynchronisation in
the productivity convergence path.

**Workaround:** `config.MACROFISCAL_YEAR_MAX = 2029`. The new vintage is truncated
to the same horizon as the old one. This has a side benefit for the sanity
comparison — old vs new differ only by data revision, not by horizon.

**Proposed fix:** thread a single `weo_max_year` through `run_pipeline()` into
`productivity_country()` and `_build_climate_variation()`, derived once from the
macrofiscal data. Then bump `MACROFISCAL_YEAR_MAX` to 2031 and the Explorer gains
two more years of IMF projections.

## 2. Duplicate `iso3c` keys crash `run_pipeline` for Serbia

**Expected:** every selectable country runs.

**Found:** `scripts/extract_excel_data.py` maps "Kosovo" to `SRB` via
`pycountry.search_fuzzy`, so the frozen `demography.parquet` has 1,359 duplicate
`(iso3c, years, age_group, status)` keys and `climate.parquet` has 510 duplicate
`(iso3c, climate_scenario, years)` keys — all under `SRB`.

`demography_country()` pivots on `age_group` without deduplicating, so Serbia
raises `ComputeError: aggregation 'item' expected no or a single value, got 2
values`. Serbia is in the app's country dropdown. Selecting it breaks the
Explorer.

**Workaround:** fixed in the new vintage. WEO April 2026 reports Kosovo as `KOS`,
mapped to `XKX`; WPP 2024 reports it as `XKX`; and carried-forward climate drops
the duplicate keys keeping the last row per key — which is the genuine Serbian
series, since the workbook lists Kosovo first and its climate rows are all zero.
Serbia now runs. Kosovo is not selectable, because there is no Kosovo
productivity or climate data to pair with it.

**Proposed fix:** the frozen vintage stays broken until it is re-extracted. If
Serbia matters before then, `_MANUAL_ISO3C["Kosovo"] = "XKX"` in
`scripts/extract_excel_data.py` plus a re-run would fix it, but that regenerates
the golden-master input data, so it is a deliberate decision rather than a
drive-by fix.

## 3. 20 of 175 selectable countries fail on missing WEO series

**Expected:** `get_country_list()` returns countries the pipeline will not crash
on — its docstring says exactly that.

**Found:** it only checks that a country appears in all four sources, not that the
rows it needs are non-null. 24 of 175 countries fail on the **frozen** Oct 2024
vintage, 20 of 175 on the new one:

```
AFG ARM BFA BGD BLR DJI HKG KAZ LBY MAC MNG MRT PRI PSE SGP SOM TGO TLS WSM ZMB
```

Two failure modes, both pre-existing and both data-driven rather than
vintage-driven:

- `TypeError: float() argument must be ... not 'NoneType'` — `baseline_v1` calls
  `float(row["real_gdp"])` on a null. `_build_macrofiscal_for_baseline` filters
  null *growth* columns but not null *levels*.
- `KeyError: 2009` — the country has no WEO row at all for the start year, so the
  lookup dict has a hole.

Hong Kong, Macao and Singapore, for instance, simply have no general government
debt series in WEO. No pipeline can conjure that.

**Workaround:** none needed for this lane's deliverables; the refresh does not
make it worse and fixes four (LBN, LKA, SRB, SYR). Reported so it is not
mistaken for pipeline damage.

**Proposed fix:** either make `get_country_list()` check for the non-null rows the
engine actually needs, or have `baseline_v1` fail with a message naming the
country and the missing series. The current behaviour surfaces to a Ministry of
Finance user as a raw Python traceback in the Explorer.
